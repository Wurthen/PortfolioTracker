## 2. Corrección financiera

### F1 · [ALTA] El coste base se infla con SafeBack

`TransactionService.AddSafeBackAsync` (líneas 213-218) añade participaciones pero **no ajusta `PurchasePrice`**:

```csharp
item.Shares += tx.Shares;          // suben las participaciones
item.SafeBackAmount += tx.AmountEur;
item.SafeBackShares += tx.Shares;
// PurchasePrice NO se toca
```

Sin embargo el coste se calcula como `Shares * PurchasePrice + Commission` en:

- `PortfolioService.MapToDto` (`PortfolioService.cs:63`)
- `PortfolioService.ComputeSinceInception` (`PortfolioService.cs:102`)

Al crecer `Shares` sin diluir el precio medio, el coste sube justo por el importe del SafeBack, contradiciendo el modelo documentado ("SafeBack no sube coste") y **hundiendo la rentabilidad**.

**Evidencia concreta:** `scripts/rebuild_gold.sql` siembra 3,91342593 acciones a 71,9446 € = **281,5 € de coste**, cuando lo invertido real fueron 5 × 50 € = **250 €**. La diferencia (~31,55 €) es exactamente el `SafeBackAmount`. Es decir, la fila de oro arrastra ese error.

**Fix propuesto:** recalcular en `AddSafeBackAsync`:

```
PurchasePrice = (Shares * PurchasePrice) / (Shares + safebackShares)
```

o, más robusto, derivar el coste de las transacciones (compras + comisiones) en lugar de `Shares * PurchasePrice`.

**Deuda relacionada:** `scripts/recalculate_safeback_costbasis.sql` es un parche manual frágil: hay que recordar ejecutarlo tras cada SafeBack, y además **omite las comisiones** (usa solo `AmountEur`, no `AmountEur + Commission`). Cualquier SafeBack nuevo vuelve a romper la consistencia.

### F5 · [MEDIA] Dos métricas para la misma ventana

- La tarjeta "Rentabilidad por periodo" usa **MWR / Modified Dietz** para 1S–1A (`Home.razor.PeriodReturn` → `period.MwrPct`).
- El gráfico en modo "Rentabilidad" usa **TWR** (`ReturnCalculators.ComputeTwrSeries`).

Tras el arreglo de "Desde inicio" (sesión 10/09), solo esa fila coincide. Un "1M" de la tarjeta y un "1M" del gráfico seguirán mostrando números distintos. Hay que decidir una métrica por contexto y etiquetarla, o mostrar ambas con su nombre explícito.

### [MEDIA] TWR pierde flujos en fechas sin punto histórico

`ReturnCalculators.ComputeTwrSeries` (línea 36) resta el flujo solo si existe un punto con esa fecha:

```csharp
var flow = flowsByDate.GetValueOrDefault(current.Date, 0m);
```

Pero itera las fechas del histórico. Una compra en fin de semana/festivo (o cuyo instrumento no tenga punto ese día) cae en una fecha sin punto → el flujo nunca se resta → **TWR inflado**. Fix: mapear los flujos a la fecha de punto anterior/siguiente, o construir el diccionario de flujos sobre las fechas de `totals`.

### [BAJA] Inconsistencia de comisión entre series

`ComputeItemReturnSeries` usa `AmountEur` (sin comisión) como coste; `ComputeSinceInception` incluye `Commission`. Los dos "costes" no son el mismo número.

### [BAJA] SafeBack fuera de XIRR

`TransactionService.GetExternalFlowsAsync` solo considera Buy/Sell, así que SafeBack no entra en XIRR. Es coherente con "SafeBack es rendimiento", pero conviene dejarlo documentado para evitar confusión futura.

## 3. Infra / build

### F3 · [ALTA] Dockerfile del API copia fuera del build context — CONFIRMADO

`docker-compose.yml` usa `context: ./src/PortfolioTracker.Api`, pero el Dockerfile intenta copiar un proyecto hermano:

`src/PortfolioTracker.Api/Dockerfile:8`
```dockerfile
COPY ["../PortfolioTracker.Blazor/PortfolioTracker.Blazor.csproj", "../PortfolioTracker.Blazor/"]
```

Comando reproducido:
```
docker build -t pt-audit-api "src/PortfolioTracker.Api"
```

Salida (extracto):
```
#11 [build 4/8] COPY [../PortfolioTracker.Blazor/PortfolioTracker.Blazor.csproj, ../PortfolioTracker.Blazor/]
#11 ERROR: failed to calculate checksum ... "/PortfolioTracker.Blazor/PortfolioTracker.Blazor.csproj": not found
ERROR: failed to build
```

**Conclusión:** el build falla siempre. El API **no** referencia el proyecto Blazor, así que la línea sobra sin más.

### F2 · [ALTA] Dockerfile de Blazor usa `--no-build` sin build previo — CONFIRMADO

`src/PortfolioTracker.Blazor/Dockerfile:10`
```dockerfile
RUN dotnet publish "./PortfolioTracker.Blazor.csproj" -c Release -o /app/publish --no-build /p:UseAppHost=false
```

No existe un `dotnet build` previo (el Dockerfile del API sí lo tiene). Comando reproducido:
```
docker build -t pt-audit-blazor "src/PortfolioTracker.Blazor"
```

Salida (extracto):
```
#14 [build 6/6] RUN dotnet publish "./PortfolioTracker.Blazor.csproj" -c Release -o /app/publish --no-build ...
error MSB4018: ... Microsoft.NET.Build.Tasks.ResolvePackageAssets ...
ERROR: process "/bin/sh -c dotnet publish ... --no-build ..." did not complete successfully: exit code: 1
```

**Conclusión:** el build falla siempre. Además, el `COPY . .` arrastra `bin/`/`obj/` del host si existen, lo que hace el resultado dependiente de la máquina.

### F4 · [MEDIA] `docker-compose.yml` sin healthchecks

`depends_on: postgres` solo espera al arranque del contenedor, no a que Postgres acepte conexiones. El API ejecuta `db.Database.Migrate()` al arrancar (`Program.cs:45`); si Postgres aún no está listo, el API cae en bucle. Falta un `healthcheck` con `pg_isready` y `condition: service_healthy`.

### F6 · [MEDIA] Claves placeholder "válidas" en `appsettings.json`

`appsettings.json` define las claves como `"SET_IN_USER_SECRETS"` (cadena no vacía). Los proveedores solo se saltan la llamada si la clave es null o vacía:

```csharp
if (string.IsNullOrWhiteSpace(_apiKey)) { ... return null; }
```

Por tanto, en `dotnet run` **sin** user-secrets se hacen llamadas reales con clave inválida (gasto y ruido de logs). Usar `""` o eliminar la propiedad.

### Otras observaciones de infra

- **`UseUrls` hardcodeado** en `PortfolioTracker.Blazor/Program.cs:8` (`http://0.0.0.0:8081`): pelea con `launchSettings` (5115) y con `ApiBaseUrl` (default 8080 frente a los 5208 del API).
- **`Antiforgery.Key` hardcodeado** en `Blazor/appsettings.json:9-11` ("PortfolioTracker_SuperSecretKey_..."), y probablemente no se usa (ASP.NET gestiona antiforgery con DataProtection). Config muerta con "secreto" falso.
- **Chart.js desde CDN** sin `integrity`/`crossorigin` (`App.razor:21`) mientras Bootstrap es local; sin red no hay gráfico de distribución.
- **Mismatch de paquetes:** `Microsoft.EntityFrameworkCore.Design 10.0.10` vs `Npgsql.EntityFrameworkCore.PostgreSQL 10.0.0` → warnings MSB3277 de unificación al compilar tests. Alinear a 10.0.x.
- **CI** (`.github/workflows/ci.yml`) correcto (restore/build/test, sin claves), pero no ejecuta analizadores ni `dotnet format`.

## 4. API / diseño / seguridad

### F4 · [ALTA si se expone] Sin autenticación

- No hay autenticación ni autorización: el `userId` viaja en la URL y no se valida contra ninguna identidad.
- CORS `AllowAnyOrigin().AllowAnyMethod().AllowAnyHeader()` (`Program.cs:30-38`).
- No hay `UseHttpsRedirection` en el API.

Aceptable para una app local personal; **bloqueante** si en algún momento se expone fuera de localhost.

### F6 · [MEDIA] GET con efectos secundarios

- `PortfolioService.GetDashboardAsync` llama a `SaveDailySnapshotAsync` en cada carga → escribe en BD, y dispara fetch de precios en vivo para todas las posiciones → quema cuota de proveedores en cada refresco de UI.
- `TransactionService.ComputeDetailedPerformanceAsync` invoca `EnsureSeededAsync`, que **crea transacciones** sintéticas si no existen.

GET que muta y consume APIs de terceros rompe idempotencia y cachés. Considerar POST explícito o un job en background.

### [MEDIA] Endpoint y código muertos

- `GET /api/portfolio/{userId}/performance` → `PortfolioService.GetPerformanceAsync` calcula valores y **los descarta** (devuelve el DTO por defecto en ceros). Además dispara fetch de precios sin utilidad.
- Los campos `Daily/Weekly/Monthly/Ytd/Yearly` de `PortfolioPerformanceDto` no se consumen en la UI.
- `PortfolioApiService.GetPerformanceAsync` no tiene ningún llamador.
- `YahooFinanceService.GetQuoteInfoAsync` y `GetHistoricalPriceAsync` no tienen llamadores.

### [MEDIA] Normalización de símbolos duplicada

La lógica `0P*` / `.EUFUND` / quitar sufijo está repetida en al menos cinco sitios:

- `PortfolioService.NormalizeSymbol`
- `CompositePriceProvider.NormalizeFundSymbol` + `IsFundSymbol`
- `AlpacaPriceProvider.IsFundSymbol`
- `YahooFinanceService.NormalizeFundSymbol`
- checks `0P` inline en `TwelveDataPriceProvider`, `HistoryBackfillService` y `EodPriceProvider`

Riesgo alto de divergencia. Extraer un `SymbolClassifier` único.

### [BAJA] Fallback de símbolo alternativo inútil

`PortfolioService.GetCurrentPriceUsdAsync` (línea 51): si EOD falla para el símbolo alternativo, reintenta el composite **con el mismo símbolo alternativo** (p. ej. un ISIN), no con `item.Symbol`. El fallback casi nunca resolverá.

### [BAJA] Sin `CancellationToken` en ninguna capa

El backfill de 12 meses puede superar el timeout de 30 s del `HttpClient` del Blazor (`PortfolioApiService`, cliente "Api"). El POST se cancela en el cliente pero **sigue ejecutándose en el servidor**.

## 5. Frontend Blazor

- **`Home.razor` es un monolito (~960 líneas):** carga de datos, orden, modo del gráfico, modales, toasts y transacciones en un solo componente. Extraer a un `HomeState`/view-model y subcomponentes.
- **`AddItemDialog.SetParametersAsync:263-272`** re-aplica la preselección en cada render (Home nunca limpia `addToExistingItemId`): si abres "Añadir a existente" y cambias a "Nueva inversión", cualquier re-render del padre lo revierte. Guardar `_lastPreselectedId`.
- **`RefreshPortfolio` sin serialización:** puede haber llamadas solapadas (OnAfterRender, callbacks de diálogos, backfill) y ganar la respuesta más lenta. Semáforo o token de generación.
- **`TransferDialog` (líneas 103-110)** no valida origen ≠ destino ni aplica el importe máximo que muestra en pantalla, y lista todos los items en vez de solo fondos.
- **`Home.DeleteItem` (línea 914)** ignora el `bool` de `DeleteItemAsync` y refresca como si hubiese ido bien.
- **Fire-and-forget** `_ = LoadItemTransactionsAsync` (`Home.razor:528`) sin `try/catch` (mitigado por el guard interno).
- **`ex.Message` volcado a la UI** en varios diálogos y en `Home` → fuga de detalles internos.
- **Placeholders activos:** `ImportButton` / `ImportDialog` / `PortfolioSelector`; `OnSelectionChanged` sin enlazar en `MainLayout.razor:11`.
- **Accesibilidad:** modales sin `role="dialog"`/`aria-modal` ni cierre con `Escape`; `btn-close` sin `aria-label`; `blazor-error-ui` duplicado en `MainLayout.razor.css` y `app.css`; `:focus` de `h1` eliminado.
- **`charts.js`:** colores hardcodeados que duplican tokens de `app.css`. (Nota: sí destruye la instancia anterior con `allocationChart.destroy()`, así que no hay bug de "canvas already in use".)
- **`IsFund` con `.Equals` sobre `Type` nullable** (`AddItemDialog:197`, `EditItemDialog:118`) → potencial NRE si `Type` fuese null.
